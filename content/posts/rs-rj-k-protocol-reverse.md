> 设备：仁科网络型 8 路水浸报警模块（网线接入）
> 目标：不跑官方那个臃肿的 exe，用自己的 Python 项目直接收设备数据
> 结果：完全逆向私有协议，自建 server 与官方应答逐字节一致

## 一、背景

机房里装了一个仁科的水浸报警器，网线接入局域网。按官方方案，必须在服务器上常驻他们的 **RS-RJ-K 环境监控平台**——一个 Windows exe，界面老旧、功能臃肿，而我的机房监控本来就是自建的 Python 平台（Flask + PostgreSQL + APScheduler），温湿度、UPS、打印机都在里面。再跑一个官方 exe 实在别扭。

官方倒是提供了一份《RS-RJ-K 二次开发接口》，但看了一眼：那只是 **exe 对外的 HTTP API**，前提还是得跑官方软件。真正有价值的文档——设备与服务器之间的**私有 TCP 协议**——并不在资料里。

于是决定：抓包，自己逆向。

## 二、先摸清架构

翻遍两份官方 PDF + 网上公开的产品手册，拼出了完整架构：

| 端口 | 用途 |
|---|---|
| **2404** | **设备上传数据端口**（TCP Server，设备作为 Client 主动连） |
| 88 | web 访问 |
| 9001 | 二次开发 HTTP API |
| 9901 / 8900 | web 内部通讯 |

关键信息来自产品手册的只言片语：

- 设备作为 **TCP Client**，上电后主动连接配置的"目标 IP:端口"（默认 2404）
- 连上后周期发送：**登录帧**（默认 3s 间隔）、**心跳帧**（60s）、**数据帧**（5~20s）
- "终端地址"为 **8 位**，服务器靠它区分设备

也就是说，官方 exe 干的核心事情就是：监听 2404，解析这三种二进制帧。只要搞清楚帧格式，我就能写一个自己的。

![官方方案 vs 自建方案架构对比](/images/rs-rj-k/img_arch.png)

## 三、被动抓包：不动现有环境

设备正在往官方 server 发数据，我不能停服务、也不想改设备配置。解决办法是**旁路嗅探**：用 Windows 原始套接字把发往 2404 端口的流量复制一份看，官方软件完全无感。

```python
sock = socket.socket(socket.AF_INET, socket.SOCK_RAW, socket.IPPROTO_IP)
sock.bind((local_ip, 0))
sock.ioctl(socket.SIO_RCVALL, socket.RCVALL_ON)   # 网卡混杂模式，需管理员
```

然后手工解析 IP/TCP 头，过滤 2404 端口，把载荷 dump 成 hex。几十行就够，不需要 npcap。

> 踩坑：Python 3.14 移除了 `socket.IPPROTO` 旧别名，要用 `socket.IPPROTO_IP`。

## 四、第一桶金：登录帧

嗅探立刻出货，设备每 5 秒发一轮：

```
设备 -> 服务器 (39 字节)
68 88 88 88 88 88 88 68 A0 1B 36 1D 34 34 33 33
33 39 39 33 33 33 33 33 33 33 33 33 33 33 33 33
33 87 A8 3A 43 F7 16

服务器 -> 设备 (18 字节)
68 88 88 88 88 88 88 68 20 06 36 1D 87 A8 3A 43
25 16
```

肉眼分析 + 程序验证，帧结构浮出水面：

```
68 88 88 88 88 88 88 68   帧头（固定 8 字节）
A0                        命令字（A0=设备上报/登录，20=服务器应答）
1B                        载荷长度（27 = 后面 payload 字节数）
36 1D ...                 载荷
F7                        校验
16                        帧尾（固定）
```

![RS-RJ-K 私有协议帧格式](/images/rs-rj-k/img_frame.png)

载荷的构成：

- `36 1D`：会话标识，服务器应答时**原样回带**
- 中间 21 字节 ASCII：`"44333993" + "3"*13` —— 前 8 位就是终端地址，后面是填充
- `87 A8 3A 43`：设备令牌，应答同样回带

服务器应答就是回显会话号 + 令牌，非常简单。

![设备与服务器的交互时序](/images/rs-rj-k/img_seq.png)

## 五、破解校验算法

校验字节怎么算的？先猜最简单的：**帧内所有字节求和取低 8 位**。

```python
sum(frame[:-2]) & 0xFF   # 去掉校验和帧尾，求和
```

- 服务器应答：算出 `0x25`，实际 `0x25` ✅
- 设备登录帧：算出 `0xC4`，实际 `0xF7` ❌ 差 0x33

差值恰好是 0x33——一个 `'3'` 的 ASCII！回头数了一遍，是我**手工抄 hex 时漏了一个字节**（21 字节的状态区被我抄成 20 字节）。从日志原样重新构造帧后：

- 设备登录帧：`sum = 0xF7` ✅

**校验算法确认：`chk = sum(帧头..载荷) & 0xFF`**。两帧全部验证通过。

这个过程有个教训：逆向时"对不上"先别怀疑算法，先怀疑自己的样本抄写。差值本身（0x33 = 恰好一个填充字符）就是线索。

## 六、触发报警：拿到状态帧

光有登录握手不够，得知道**水浸状态编码在哪**。让嗅探器持续跑，湿纸巾贴探头触发报警（官方软件同步弹窗确认链路），对比报警前后的帧：

```
正常:  ... 36 1D | 34 34 33 33 33 39 39 33 33*13 | 87 A8 3A 43 | F7
报警:  ... 36 1D | 34 1B 36 34 33 39 39 73 33*13 | 87 A8 3A 43 | 22
                ^^  ^^  ^^          ^^
```

状态区有 4 个字节同时变化（`34→1B`、`33→36`、`33→34`、`33→73`）。这台是 **8 路设备**，状态位是打包编码的；当前只接了第 1 路，得到可用的判定规则：

![报警前后状态区字节对比](/images/rs-rj-k/img_alarm.png)

```python
def check_alarm_ch1(field: bytes) -> bool:
    return len(field) >= 8 and (field[1] == 0x1B or field[7] == 0x73)
```

> 诚实说明：校验字节有三种观测值 F7（正常）/ E2（过渡）/ 22（报警），其中 E2 帧与 F7 帧**内容完全相同但校验不同**，说明校验可能混入了帧外状态，尚未完全弄清。但校验只用于**接收端验证**，报警判定只依赖状态区字节，不影响功能。以后启用第 2~8 路时，逐路触发采样即可建立完整映射。

## 七、自建 server

核心逻辑其实非常薄：

```python
def build_ack(session, token):
    payload = session + token
    frame = bytearray(HDR)          # 68 88*6 68
    frame.append(0x20)              # 应答命令
    frame.append(len(payload))
    frame += payload                # 回显会话号 + 令牌
    frame.append(sum(frame) & 0xFF)
    frame.append(0x16)
    return bytes(frame)
```

完整实现（约 200 行，纯标准库）：

- TCP 监听 2404，多线程接入设备
- 收到 `A0` 帧 → 校验 → 解析状态 → 状态变化时输出 JSON 事件 → 回应答
- 事件写入 `leak_events.log`：`device_online` / `status`（含报警判定）/ `device_offline` / `bad_checksum` / `unknown_cmd`
- 内置 `--selftest`：用抓包得到的真实帧离线回放，验证解析、校验、报警判定、应答构造

自测结果：

```
[PASS] normal alarm=False chk_ok=True ack_match=True
[PASS] alarm  alarm=True  chk_ok=True ack_match=True
2/2 tests passed
```

其中 `ack_match=True` 是最有意思的一项：**我们构造的登录应答与官方服务器实际发出的应答逐字节相同**。设备完全无法区分对面是官方 exe 还是 200 行 Python。

## 八、验证方法（给要复现的人）

1. 管理员运行嗅探脚本，确认每 5 秒能看到登录帧滚动
2. 停掉官方 RS-RJ-K（释放 2404），启动自建 server
3. 设备 5 秒内重连，日志出现 `device_online` + 首条 `NORMAL`
4. 湿纸巾触发报警 → `status: ALARM`；擦干 → 恢复 `NORMAL`

事件格式：

```json
{"event": "status", "ip": "10.241.3.100", "terminal_addr": "44333993",

```
